# DP.FM.283 — Self-test инструмента с захардкоженной авторской fixture: ложный отказ на чужой инсталляции

## Паттерн

Self-test тиражируемого инструмента проверяет наличие конкретных данных из окружения автора (номер РП, путь к файлу, ID артефакта) — вместо синтетической fixture или инвариантов.

На любой чужой инсталляции диагностика даёт **ложный отказ**: данные автора отсутствуют → self-test «падает» → пользователь теряет доверие к инструменту как сигналу.

## Инцидент

`wp-sync-bundle.sh --self-test` проверяет захардкоженный WP-294 (авторский РП, отсутствует на пользовательских инсталляциях). На чужом IWE скрипт всегда падает.

## Диагностика

**Тест:** «Self-test запускается на инсталляции без авторских данных и падает?» Да → DP.FM.283.

Симптом: диагностическая команда `--self-test` возвращает non-zero exit code или error message без каких-либо реальных проблем в инструменте.

## Fix

Self-test инструмента должен:
1. Создавать **собственную синтетическую fixture** (временный файл, тестовые данные) при старте
2. Проверять **структурные инварианты** (формат файла, наличие секций, корректность парсинга), а не конкретные значения из авторской среды
3. Удалять fixture после проверки

Антипаттерн: `if [ -f "$WP_DIR/WP-294.md" ]; then...` → паттерн: создать `mktemp`, наполнить тестовыми данными, проверить, удалить.

## Правило

**Self-test не ссылается на авторские данные.** Только синтетические fixtures или инварианты формата.

## Применимость

Любой CLI-инструмент с `--self-test` / `--check` / `--validate`, предназначенный для тиражирования (IWE скрипты, шаблонные утилиты, CI/CD gates).
