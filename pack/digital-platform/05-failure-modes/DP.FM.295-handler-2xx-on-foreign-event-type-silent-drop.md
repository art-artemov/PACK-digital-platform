# DP.FM.295 — Обработчик отвечает 2xx на «чужой» тип события

## Паттерн

Консьюмер фильтрует события по типу и на неподходящий тип отдаёт успех (`200 OK`, `ack`, `commit offset`). Пока он один из нескольких приёмников — поведение корректно. Как только он становится единственным, тот же код превращается в **тихий сток**: провайдер видит успех и не повторяет доставку, лог фиксирует «received», дальше ничего не происходит.

## Почему невидим

- Провайдерский retry погашен собственным ответом — события не возвращаются.
- Кода ответа 5xx нет → внешний мониторинг зелёный.
- В логе есть запись о приёме → поиск «а приходило ли событие?» даёт «да».

Обнаруживается только по жалобе конечного потребителя (в WP-82 — покупатель без товара, 9.5 часов).

## Правило профилактики

«Не мой тип» и «обработано» обязаны различаться:

| Ситуация | Ответ | Наблюдаемость |
|----------|-------|---------------|
| Тип обработан | 2xx | счётчик обработанных |
| Тип известен, но не мой (есть второй приёмник) | 2xx | отдельный счётчик «пропущено по типу» |
| Тип неизвестен | 2xx + **алерт** | событие в трекер ошибок |

Неизвестный тип — сигнал, а не успех. Ранний `return true` по любому признаку (`isSubscription`, `productType`, платформа) — красный флаг при ревью.

## Область применения

Любой консьюмер с фильтром по типу: вебхуки платёжных провайдеров и сторов, подписчики Kafka/Redis, роутеры очередей, GitHub/GitLab hooks.
