# DP.FM.296 — Класс отказов: релиз меняет контур, HTTP-мониторинг зелёный, ломается только функциональность

## Паттерн

Релиз переносит поток данных на новый контур (новый источник настроек, новый адрес вебхука, новый обработчик) — старый контур обесточен. Ни один внешний индикатор состояния сервера (код ответа, доступность страниц, отсутствие 5xx) не смотрит на сам поток данных: сервер отвечает 200, страницы открываются, а функциональность внутри молча не работает.

## Диагностика

**Тест:** «Релиз меняет ИСТОЧНИК или АДРЕС, откуда/куда идёт поток данных (конфигурация, вебхук, интеграция), при этом сохраняя HTTP-контракт сервера неизменным?» Да → предполётный чек-лист вида «после выката 500-х нет, главная отвечает 200» этот класс отказа не ловит по конструкции.

**Инструмент:** прогнать один реальный экземпляр потока (событие, покупку, чтение конкретной настройки) — не проверять состояние сервера.

## Инциденты (два случая одного класса, один день — 2026-08-10)

1. **WP-74** — релиз перевёл код на новый источник настроек (`Option::get()` без фолбэка на старый `Configuration::getValue`); 40 опций `hdc.core` не заполнены. Молча деградировали SmsAero, Telegram, Firebase-пуши, валидация покупок, Turnstile, сокращалка ссылок, аналитика. Сайт отвечал 200 всё это время. → `memory/lessons_config-source-migration-no-fallback.md`.
2. **WP-82** — релиз переключил адрес вебхука IAPHub на новый приёмник (обслуживал только подписки); разовые покупки перестали начисляться на 9.5 часов. Сервер отвечал 200 на каждое отброшенное событие. → DP.FM.295, `memory/lessons_webhook-endpoint-switch-event-coverage.md`.

Оба обнаружены через внешнюю жалобу, не через мониторинг — время до обнаружения 9.5 ч и ~2 суток соответственно.

## Правило

**Если релиз переносит поток данных на новый контур (источник конфигурации, адрес интеграции, обработчик) — приёмочная проверка обязана прогнать один реальный экземпляр потока, а не проверять состояние сервера.** HTTP-мониторинг (код ответа, аптайм) структурно не видит эту категорию отказов.

## Применимость

Любой релиз со сменой контура: миграция источника настроек, переключение адреса внешнего вебхука/коллбэка, замена обработчика интеграции, cutover между старой и новой версией внешнего API. Особенно опасно в монолитных legacy-системах, где смена контура — точечная правка кода без структурного изменения (не видна как «новая фича» в диффе).
