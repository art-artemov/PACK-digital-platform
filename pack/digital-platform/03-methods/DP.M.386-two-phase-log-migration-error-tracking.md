# DP.M.386 — Двухфазная миграция на error-tracking с файлами как fallback

## Определение

Стратегия перехода от файловых логов к централизованному error-tracking: переходный период с двойной записью, затем файл становится fallback-каналом (пишет только при недоступности трекинга). Файловый лог не убирается — он единственный канал при сбое самого трекинга.

## IPO

- **Вход:** приложение с файловыми логами ошибок, без error-tracking
- **Процесс:** двухфазный переход с сохранением файлового fallback
- **Выход:** centralized error-tracking как primary, файл как self-диагностика недоступности трекинга

## Фазы

**Фаза 1 — Двойная запись (2–4 недели):**
- Ошибка → записывается И в файл, И в error-tracking
- Цель: убедиться, что трекинг работает, охват полный, потерь нет

**Фаза 2 — Файл как fallback:**
- Ошибка → в error-tracking (primary)
- Если SDK вернул `null` (доставка не удалась) → в файл
- Целевое состояние: файлы перестают расти в норме

## Ключевое свойство: самодиагностика

«Появился файл → доставка в трекинг сломалась». Файл становится сигналом сбоя, а не основным хранилищем. Это повышение наблюдаемости, а не усложнение.

## Почему не убирать файлы совсем

Error-tracking server = единственный инстанс на другом хосте. Сбой сети/контейнера трекинга → именно в этот момент теряются критические ошибки (те, ради которых всё затевалось). Файл — единственная страховка для этого сценария.

## Проверка SDK fallback

`captureException()` возвращает `null` при сбое доставки (подтверждено по коду Sentry PHP SDK). Проверено на практике: при TLS-сбое первого прогона событие ушло в файл, не потерялось.

## Режимы хендлера

| Режим | Описание |
|-------|----------|
| `always` | Пишет и в файл, и в трекинг (Фаза 1) |
| `fallback` | Только при сбое трекинга (Фаза 2, целевое) |
| `off` | Без файлов (только теоретически, не рекомендуется) |
