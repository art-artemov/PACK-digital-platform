# DP.M.384 — Control Plane / Delivery Plane — паттерн асинхронной доставки поверх legacy CMS

## 1. Определение

Гибридный архитектурный паттерн: legacy-монолит остаётся **control plane** (данные, UI, логика), тяжёлая асинхронная доставка выносится в **delivery plane** (отдельный сервис). Связь — REST-контракт между плоскостями.

## 2. Проблема

Legacy-монолит (CMS, ERP) содержит аудиторию, бизнес-логику и UI, но не способен масштабировать асинхронные операции (push-рассылка 150k+ токенов, batch email) без риска заблокировать основной процесс и без инфраструктуры ретраев, backoff и feedback-цикла.

## 3. IPO-паттерн

| Элемент | Описание |
|---------|----------|
| Входы | Команда от control plane: что доставить, кому, когда (идемпотентный батч с batchId и cursor) |
| Обработка | Delivery plane: очередь → воркеры → внешний провайдер (FCM, SMTP, SMS) → feedback |
| Выходы | Статистика, статусы доставки → обратно в control plane через feedback-канал (порции + `final: true`) |

## 4. Шаги применения паттерна

1. **Разграничить ответственности.** Control plane: аудитория, сегменты, расписание, диспетчер. Delivery plane: очередь, ретраи, провайдер API, feedback.

2. **Определить REST-контракт.** Control plane режет аудиторию на идемпотентные батчи фиксированного размера (1000 токенов). Каждый батч несёт `batchId` для идемпотентности на delivery-стороне. Кампания хранит cursor прогресса.

3. **Реализовать feedback-канал.** Delivery plane периодически (window ~30с) отправляет статистику назад в control plane. Последняя порция несёт флаг `final: true` — signal завершения потока без polling.

4. **Обеспечить изоляцию сбоев.** Падение delivery plane не ломает монолит. Cursor позволяет возобновить рассылку с того же места. Идемпотентность батчей предотвращает дубли при retry.

5. **Эволюция независимо.** Delivery plane можно заменить или масштабировать без изменений в монолите — только контракт неизменен.
