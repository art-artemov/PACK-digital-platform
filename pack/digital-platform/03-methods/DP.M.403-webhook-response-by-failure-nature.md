# DP.M.403 — Ответ вебхук-приёмника по природе сбоя

## Описание

Приёмник событий от внешнего провайдера выбирает код ответа по одному критерию: **изменит ли повторная доставка результат**. Факт ошибки сам по себе кода ответа не определяет.

## Алгоритм

### Шаг 1: Классифицировать сбой

| Класс | Примеры | Изменит ли повтор результат |
|-------|---------|-----------------------------|
| Транзиентный | Апстрим недоступен, таймаут, сетевой сбой | Да |
| Детерминированный | Payload невалиден, чек отклонён стором, неизвестный продукт | Нет |

### Шаг 2: Назначить ответ

| Класс | Ответ | Дополнительно |
|-------|-------|---------------|
| Транзиентный | 5xx | Повтор делает провайдер — собственная очередь ретраев не нужна |
| Детерминированный | 2xx | Обязательное событие в трекер ошибок (Sentry/GlitchTip) |

### Шаг 3: Проверить отсутствие анти-паттерна

Единая ветка `catch` с ответом 200 и записью в файловый лог — оба класса становятся невидимы: транзиентный сбой теряет событие (повтора не будет), детерминированный не поднимает алерт.

Обратный анти-паттерн — 5xx на детерминированный отказ: провайдер повторяет тот же payload с тем же результатом, создавая шум ретраев и отравляя очередь доставки.

## Условие применимости

Метод опирается на провайдерский retry. Если провайдер не повторяет доставку по 5xx — транзиентный класс требует собственной durable-очереди (см. DP.M.333, режим fail-queue).

## Область применения

Платёжные вебхуки, вебхуки сторов, GitHub/GitLab hooks, callback'и служб доставки — любой внешний приёмник с retry на стороне провайдера.
