# DP.M.391 — Флаг `required` в справочнике типов уведомлений вместо hardcode-исключений

## Определение

Реализация требования «маркетинговые уведомления — только opt-out»: обязательность типа (нельзя отключить) хранится в справочной таблице как флаг `required`, а не в коде как список кодов типов.

## IPO

- **Вход:** таблица типов уведомлений (`hd_push_types`) с флагом `required TINYINT(1) DEFAULT 0`
- **Процесс:** API при запросе «отписаться» читает флаг → `required=1` → 422 «обязательный тип»; `required=0` → сохраняет отписку
- **Выход:** любой тип можно сделать обязательным/опциональным правкой данных, без деплоя кода

## Ключевое свойство

Добавление нового типа или изменение его обязательности = **правка данных, не кода**.

Антипаттерн:
```php
if (in_array($typeCode, ['actions', 'transit'])) {
    throw new Exception('нельзя отменить');
}
```

Паттерн:
```php
if ($type['required']) {
    throw new Exception('нельзя отменить');
}
```

## Связь с принципом реестр-не-hardcode

Частный случай DP.ARCH.001 #7 применительно к consent-семантике: поведение системы (обязательность типа) вынесено из кода в конфигурируемый реестр. Проверяемость: можно сделать транзакционный тип опциональным без деплоя — только UPDATE в справочнике.

## Условие применения

Применять, когда:
- Список «особых» значений меняется в процессе эксплуатации
- Изменение требования «обязательный/опциональный» не должно требовать деплоя
- Нужен аудит: кто изменил обязательность и когда (история таблицы)

Не применять, когда обязательность является инвариантом системы (не меняется никогда) — там можно захардкодить.

## Применимость

Любые настройки с дефолтом, где поведение «обязательно / опционально» может меняться: фичи-флаги на уровне типа, политики согласия, обязательные атрибуты профиля.
