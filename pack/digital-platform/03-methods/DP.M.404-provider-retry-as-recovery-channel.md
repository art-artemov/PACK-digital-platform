# DP.M.404 — Провайдерский retry как канал восстановления

## Описание

После инцидента, в котором события были приняты, но не обработаны, восстановление выполняется **кнопкой повторной доставки на стороне провайдера** — без миграций, скриптов дозаписи и ручного ввода. Возможность появляется не сама собой: она заложена в конструкцию приёмника.

## Два условия приёмника

1. **Полный payload тянется из API провайдера по идентификатору события**, а не берётся из тела запроса. Тогда повтор восстанавливает актуальное состояние сам, даже если тело исходного запроса было неполным.
2. **Бизнес-даты берутся из payload события, а не из времени обработки.** Иначе восстановление искажает историю: покупка получает дату повтора вместо даты покупки.

## Следствие для проектирования

Приёмник, спроектированный так, переводит «потеряли события» из инцидента с ручным разбором в операцию на стороне провайдера. Проектное решение принимается до инцидента — после него менять конструкцию поздно.

## Ограничение

Приёмник, закрытый IP-allowlist'ом провайдера, недоступен агенту для повторной доставки — кнопка живёт в дашборде провайдера. Повтор планируется как **шаг приёмки на стороне пилота**, а не как действие исполнителя.

## Проверка

«Если удалить обработанные записи и нажать retry в дашборде провайдера — состояние восстановится полностью и с исходными датами?»
- Да → канал восстановления есть.
- Нет → инцидент потребует ручного разбора; условия 1-2 не выполнены.
