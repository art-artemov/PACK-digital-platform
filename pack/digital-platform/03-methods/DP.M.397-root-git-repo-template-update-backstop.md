# DP.M.397 — Корневой git-репо рабочей директории как backstop

## Определение

Метод защиты от тихой перезаписи файлов при шаблонных апдейтах: инициализировать git-репозиторий в корне рабочей директории IWE (не только в поддиректориях). Тогда любое `update.sh` / `template-sync.sh`, перезаписывающее файлы в корне (CLAUDE.md, MEMORY.md, settings.json), становится видимым через `git status`/`git diff` до коммита.

## IPO

- **Вход:** рабочая директория IWE без корневого git-репо; `update.sh` изменяет файлы
- **Процесс:** `git init` в корне → после каждого `update.sh` → `git diff` → сравнить изменения → rollback если нужно
- **Выход:** любое изменение в корне видно и обратимо до коммита

## Когда применять

- При первичной установке IWE
- После каждого `update.sh` / `template-sync.sh`
- При обнаружении неожиданных изменений в рабочей директории

## Контекст возникновения

До создания корневого репо единственной страховкой была «агент читал файл в начале той же сессии». Инцидент: 3-way merge при `update.sh` применил к §8/§9 CLAUDE.md (авторский контент) ту же консолидацию, что и к платформенному шаблону — тихая потеря ~90 строк авторского контента. Без корневого репо эта потеря была бы незаметна.

## Побочный эффект

`check-dirty-repos.sh` требует отдельной правки для сканирования корня — паттерн «скрипт итерирует subdirs, пропускает workspace root».
