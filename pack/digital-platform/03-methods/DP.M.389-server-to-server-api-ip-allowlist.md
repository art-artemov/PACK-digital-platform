# DP.M.389 — Server-to-server через API-хост с глобальной подписью: штатный обход через IP-allowlist

## Определение

Метод разрешения конфликта «глобальная проверка подписи клиента vs server-to-server вызов»: использовать штатный механизм исключений API-шлюза (IP-allowlist доверенных серверов) вместо отключения проверки или подделки заголовков.

## IPO

- **Вход:** API-хост с глобальным middleware, требующим заголовки мобильного/web-клиента; server-to-server вызов без этих заголовков → 501
- **Процесс:** (1) проверить прецеденты в allowlist (сервер часто уже добавлен из предыдущей интеграции); (2) если нет — добавить IP сервера в `access.api.ip` (конфигурация шлюза); (3) server-to-server вызов проходит без клиентских заголовков
- **Выход:** рабочий server-to-server канал через тот же API-хост без нарушения security-политики

## Симптом обращения

Эндпоинт реализован и отвечает на закрытом контуре (например, внутри сервера), но при вызове с другого сервера возвращает **501** — глобальный middleware хоста требует заголовки клиентского приложения.

## Важные ограничения

- **Не отключать глобальную проверку** — security-boundary для пользовательского трафика
- **Не подделывать заголовки клиента** — нарушение контракта и скрытый риск регрессий
- **Проверить прецедент перед добавлением:** `grep <server_ip> access.api.ip` — сервер может уже быть в списке из другой интеграции (избегаем дублей)

## Источник

WP-8 (e2e проверка feedback-эндпоинта): S2 (Node.js delivery plane) вызывал `/push/feedback/` на api-хосте — 501 из-за глобальной проверки подписи. S2 уже был в allowlist из WP-6 (pdf-сервис). Прецедент переиспользован без повторного добавления.

## Применимость

Любые API-шлюзы с обязательной подписью клиента (Bitrix, custom middleware), куда нужно направить трафик от доверенного внутреннего сервиса.
